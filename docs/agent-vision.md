## 1. 背景：用户与终极目标

- **用户背景**：水利工程博士，正在研究如何将本行业传统物理模型（水文模型、洪水预报模型、水动力模型等）与 AI Agent 联动。
- **终极愿景**：AI 赋能下的**数字孪生水利 / 智慧水利**。核心逻辑（未来态）：
  ```
  实时数据 → Agent → 调用多个模型 → 模拟未来72小时 → 自动提出调度方案 → 专家确认 → 执行 → 反馈学习
  ```
- **当前 RAG 系统**未来将作为 Agent 的**个性化长期知识库**——不只存水利专业知识，也存 Agent 运行中产生的有价值知识。

## 2. 现有 RAG 系统（已完成，作为 Agent 的基础设施）

- **技术栈**：FastAPI + SQLAlchemy(async) + SQLite / LangChain / BGE-M3 向量 + Chroma / BM25 / bge-reranker / DeepSeek-chat。
- **功能**：PDF（文本层 + OCR + CID 乱码检测 + 断号自检修复）、Word(.docx)、Excel(.xlsx/.csv)、Markdown、Txt 多格式解析切片；结构感知分块；混合检索（向量0.7 + BM25 0.3）+ rerank；5 种回答风格；语义缓存；知识库/文档管理。
- **问答记忆库（AI native 自身长库，已上线）**：用户 👍/👎 沉淀 good/bad 记忆，同题秒回、负面强制重检、按用户隔离、容量淘汰。**pytest 126 全绿**。
- **管理后台**：知识库管理、记忆库管理（统计/筛选/录入/纠正/导出）、账号管理（创建/角色/启停/重置密码/删除）。
- **UI**：AntD 5 深色科技主题 + 粒子登录 + 玻璃拟态。
- **测试状态**：非 OCR PDF、OCR PDF、Word、Excel 均已实测入库与精准检索。

## 3. Agent 愿景（首个 Demo）

用户以大白话提问，Agent 自动驱动洪水预报模型，走与专业从业者相同的完整流程，最后把专业数值结果翻译成普通人能看懂的语言。

**示例**：
> 用户：未来24小时我们这个水库是否会发生洪水？
> Agent 内部流程（等价于人工预报）：
> 需求解析 → 数据收集（降雨/气象/水文/库容曲线/洪水过程线/DEM）→ 数据处理（质控/插值/单位换算）→ 建模配置 → 参数率定 → 模拟运行 → 结果分析 → 调度方案计算
> Agent 转译输出：
> "未来24小时会发生洪水，将淹没到 xx 高程，需立即采取措施保障下游安全。根据水库汛期调度运用计划，可开 N 孔闸门、开度 xx、下泄 xx m³/s，提前腾出库容以应对 24 小时后的极端洪水。"

本质：把**人工驱动的预报**改为 **Agent 代替人工执行**，相同的专业流程，只是执行者从人变成 Agent 指挥各类 tool/skill/API。未来集成更多模型，实现真正的智慧水利。

## 4. 核心架构分析

### 4.1 核心认知：Agent = 把"专家人工工作流"变成"可编排的服务编排"

专业洪水预报流程的每一步都拆成 Agent 可调用的**工具/技能**：
```
需求解析 → 数据收集 → 数据处理 → 建模配置 → 参数率定 → 模拟运行 → 结果分析 → 调度建议 → 结果转译
```

### 4.2 分层架构

```
用户层：大白话提问 + 专家确认/反馈
   │
   ▼
Agent 编排层（LLM 推理核心）
   · 需求解析 → 目标拆解 → 工具编排 → 执行→观测→再决策（Agent 循环）
   · 记忆召回（RAG 增强）→ 决策
   │调用          │调用         │查询
   ▼             ▼            ▼
┌─────────┐  ┌─────────┐  ┌──────────────┐
│ 数据工具  │  │ 模型工具  │  │ 记忆/知识层   │
│ 天气API  │  │ 水文模型  │  │ 静态: 规范/   │
│ 水文监测  │  │ 汇流模型  │  │     调度计划/ │
│ 库容/DEM │  │ 水动力模型│  │     模型手册  │
│ 质控/插值│  │ 参数率定  │  │ 动态: 历史预报│
│ 单位换算  │  │ 调洪演算  │  │     案例/决策/│
└─────────┘  └─────────┘  │     结果/反馈  │
                          └──────────────┘
   │             │
   ▼             ▼
模型服务层：物理模型包成"可调用服务"（标准化输入/输出契约）
   │
   ▼
数据层：实时数据（降雨/水位/流量）+ 静态数据（DEM/库容曲线/河网）
```

### 4.3 各层职责

- **编排层**：LLM 做规划与决策，负责任务分解、工具选择、顺序编排、结果校验、人话转译。
- **数据/处理工具层**：数据获取（气象/水文 API）、质控、插值、单位换算、格式转换。
- **模型执行工具层**：水文模型（如新安江）、汇流模型（如 Muskingum）、水动力模型、参数率定（如 SCE-UA/NSGA-II）、调洪演算。
- **模型服务层**：把物理模型包成输入/输出标准化的可调用服务（关键难点，纯领域工程）。
- **记忆/知识层**：RAG + AI native（见第 5、6 节）。

## 5. AI Native 的理解与应用（用户核心关注点）

AI native 的实质：**系统的价值来自运营累积的知识，而非初始设定**。用户认为这是改变 Agent 未来的关键技术，也是智慧水利的关键。

落到本项目：
- **每次预报都沉淀一条记忆**：输入数据、模型配置、参数、模拟结果、专家决策、事后实际结果。
- **相似情境再出现时**：召回过去案例与结果 → Agent 参考"上次这种降雨 + 前期土壤含水量，发生了什么，专家怎么处理"。
- **经验持续累积**：哪些参数组合有效、哪套调度方案效果好 → 越用越准。
- 未来演进：模型驱动结果也存为永久记忆，为 AI native 提供理论参考。

## 6. RAG 在 Agent 中的定位（存什么、起什么作用）

| 记忆类型 | 内容 | 作用 |
|---|---|---|
| **静态知识** | 规范标准、汛期调度运用计划、模型手册、流域特征、数据说明 | 回答"规程要求什么" |
| **动态经验** | 历史预报案例、每次的模型配置/参数/结果、专家决策、结果验证 | AI native 核心——"上次怎么处理、效果如何" |
| **情境记忆** | 相似水文情形的历史应对 | 决策参考——"这类情形通常如何预报/调度" |

结论：RAG 不只是水利知识库，将来就是 **Agent 的"个人长期记忆"**——既装行业专业知识，也装 Agent 自己运行产生的经验。

## 7. 五个必须正视的硬难点

1. **模型接口标准化（最难，纯领域工程）**：物理模型要变成"输入 JSON → 输出结果"的可调用服务。
2. **数据治理**：Agent 会继承人的数据问题（单位不一致、缺测、格式杂），需要质控/插值/换算工具链。
3. **信任与安全**：Agent 输出绝不能直接控制闸门，必须保留"专家确认"环节（用户已认同）。
4. **错误链传播**：预报链条长，一步错步步错，需中间校验 + 可追溯。
5. **可解释性**：预报必须能回溯依据（为什么报洪水？依据哪条数据），专家才敢签字。
